# Integration contract

Agentic Design Harness 2.0.0 bundles eleven design workflows; every skill file is pinned by
`skills-lock.json` (regenerate with `scripts/gen-lock.py`). `harness-package.json` declares the
helpers, workspace rules and execution modes those workflows resolve, for the source checkout and
for installed projects. Nothing is fetched from, or run in, another repository.

## Boundaries

- Harness: project-context discovery, routing, installation, local skill identity, persistent memory,
  objective web floor, packaging and separate-project creation.
- Bundled workflows: all eleven design procedures, creative/reference handling, principles, system
  workflows, reviews, detector and supporting scripts, authenticated by the lock.
- Host: actual file access, native registration/activation, delegation and rendering capabilities.
  A local structural check is not evidence of a live native run.

Source checkout uses `.claude/skills/` and `docs/skills-lock.json`. Installed projects use the
relative `skills_path` in `.agentic-design-harness.json` and a pinned lock at
`docs/agentic-design-harness/skills-lock.json`. The path-scoped install uses `.agents/skills/`;
its measurements resolve the same tree rather than falling back to `.claude/skills/`.
The marker is routing metadata, not proof: preflight authenticates the bytes on each check.

The workspace helper first installs the pinned workflows/context and then copies the complete
reusable template tools into the independent project, without Git history, generated dist, CI
or host files. It keeps the harness guide at HARNESS-README.md and writes a project README. The installed marker identifies that project as an existing application workspace;
normal iteration does not create another sibling. The helper refuses existing destinations and
output inside the source harness. Explicit existing-project work uses the additive installer.

## Routing choices

Routing has no reference quarantine or native-only invocation mandate. Original references remain
available through synthesis and proof-building. Discovery, study-proof principles, independent
distinctiveness/resonance review and local proof outputs are owned by the bundled workflows.
Reference study now extracts provisional per-source visual guides, preserving colour roles and
coverage, typography, components and imagery. Influence questions distinguish faithful style, loose
inspiration and deliberate compatible mixing. Early previews can pause for feedback before full
reviews, but still execute study-proof principles; a completed comparison retains its review gates.
Required execution and evidence remain real in folder mode. The compact entry keeps the persistent
context, contract protection, system lifecycle, isolated production review, bounded repair and
separated memory.

## Acceptance

`scripts/tests/wiring.py` exercises clean and existing-project installations, preserved project
files, actual Node renderer resolution under `.agents/skills`, relocation, corrupted same-named
skills, collision candidates and separate-project output. `scripts/tests/contracts.py` checks the
harness does not reinstate the reference quarantine or native-only behavior. Smoke retains the
original deliberately failing web floor fixtures. Packaging must include `integration/` so the
path-scoped installer works from the downloadable archive too.

These are integration checks, not new model evaluations. A creative acceptance run with the same
brief and references is still useful after the wiring passes. Native Claude Code/Cowork activation
is not claimed from filesystem tests. Missing renders must remain explicitly unverified.

## Release corrections

Host checking now starts at the selected host entry and requires a real route to the actual
instruction file. Missing, commented or example imports do not count. Nested imports resolve
relative to their containing file, as documented in Claude Code's memory guide:
https://code.claude.com/docs/en/memory#import-additional-files

The context budget reads the installed instruction_file rather than assuming project AGENTS.md
belongs to the design harness. Existing engineering instructions and rule files remain untouched.
The additive installer writes an integration report and uses a separate instruction namespace;
root files are never silently merged. A project owner applies its proposed canonical routing line.

New-project discovery is in PROJECT-START.md. Material brand context is gathered first, exploration
uses provisional contracts, and accepted guidelines/system work follows approval. Existing projects
consume their established context unless a change is requested.
