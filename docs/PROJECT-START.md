# Starting or joining a design project

First resolve the workspace. When opened as the reusable source harness, use
`scripts/create-project.py` and continue in its returned project_root. That project receives an
independent working copy of the harness; keep the reusable source clean. Within an installed
project, continue there. For an existing app, use the additive installer from a clean source;
read its integration report and preserve the project's development harness and existing rules.

## New product: discovery before choosing a visual solution

Read the actual brief and references. Establish the product's purpose, audience, desired outcomes,
content and primary actions; positioning, personality and voice; existing brand/system evidence;
platform, constraints and assets; and what the person delegates. Reuse answers already supplied.
Ask material missing questions together. Do not require a complete brand questionnaire for a small
page, or treat plausible business facts as verified. Capture useful context in design/product.md
and design/brief.md; keep assumptions and actual decisions distinct.

When brand direction is unresolved, explore it through the bundled direction-study workflow with
original references and suitable proofs. It stops for a person's decision. Do not create a
production system merely to begin exploration. Extract a provisional visual guide per reference
beside the actual original, following direction-study's reference-study guidance. Ask whether the
person wants faithful style, loose inspiration or compatible combinations; reuse stated intent.
Keep contrasting alternatives distinct and record material project-driven departures. Initial
rendered previews may pause for feedback with reviews pending; principles still guide building.
A request for brand discovery alone may stop at
its brief and unresolved decisions; it does not authorize an application build or publication.

After approval, ui-design-system can author visual brand/style guidelines and create or reconcile
the implementation system. A compatible machine-readable visual brand can use brand-to-system.
Document intent and relationships as well as tokens. Keep BRAND.md, DESIGN.md, tokens and existing
components as the accepted sources for future builds, reviews and drift checks. The bundled workflows' detailed
procedures own these steps; this file supplies project context, not a new design methodology.

## Existing product

Inspect its development instructions first. Inventory its actual brand, system, shipped surfaces,
components and relevant decisions; reuse them. Use system Extract if documentation is missing,
Reconcile for an accepted change, or Audit–Drift for verification. Do not run brand discovery again
unless requested or a material gap genuinely requires it. Preserve existing design context and
report disagreements rather than silently replacing it. Keep non-design engineering rules under
the development harness's ownership.
